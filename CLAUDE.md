@AGENTS.md

## Proyecto

PWA ("Mi Misa PS" en el celular) para registrar la asistencia semanal a misa de los alumnos de la pastoral de catequesis de un colegio (Confirmación y Primera Comunión). El alumno sube una foto como prueba y los guías/administradores la validan o rechazan desde un panel de revisión tipo "Tinder". Las fotos son de menores: nunca deben quedar públicas. La política de privacidad pública (`/privacidad`, `app/privacidad/page.tsx`, contacto `pastoral@ps.edu.pe`) describe lo que la app guarda de verdad: si cambian los datos que se guardan, quién los ve o dónde se guardan, actualízala junto con su fecha. Todo el dominio (rutas, componentes, tablas, variables, comentarios y textos de UI) está en español: mantener esa convención.

Stack: Next.js 16 (App Router) + React 19, TypeScript estricto, Tailwind CSS v4, Supabase (Postgres + Auth + Edge Functions + pg_cron) y Cloudflare R2 para las fotos.

## Comandos

```bash
npm run dev                          # servidor de desarrollo en http://localhost:3000
npm run build                        # build de producción (incluye chequeo de tipos)
npm run lint                         # ESLint 9 (flat config: next core-web-vitals + typescript)
npx eslint app/dashboard/page.tsx    # lint de un solo archivo
npx tsc --noEmit                     # solo chequeo de tipos
npm test                             # Vitest (archivos *.test.ts)
npx vitest run ruta/al/archivo.test.ts  # un solo test

# Supabase local (requiere Docker Desktop)
npm run db:start                     # levanta Postgres, Auth y API en http://127.0.0.1:54321
npm run db:reset                     # reaplica migraciones + supabase/seed.sql
npm run db:test                      # tests pgTAP de supabase/tests/
npx supabase test db supabase/tests/03_alumno_test.sql  # un solo archivo de tests
npm run db:types                     # regenera lib/supabase/database.types.ts
npm run functions:serve              # Edge Functions locales con supabase/functions/.env (claves R2 del token "asistencia-dev")
```

Si cambias dependencias en Windows, comprueba que el lockfile sirva en Linux antes de subir (npm en Windows a veces omite dependencias opcionales de Linux y la CI falla en `npm ci` con "Missing: … from lock file"):

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD":/app -w /app node:24 npm ci --ignore-scripts --dry-run
```

Si falla, regenera el lockfile dentro del contenedor con `npm install --package-lock-only --ignore-scripts` (en una copia de `package.json` y `package-lock.json`) y súbelo.

Variables de entorno de Next: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_GOOGLE_CLIENT_ID` y `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (ver `.env.example`; sin esta última la app no ofrece activar los avisos). Para desarrollo con Supabase local van en `.env.development.local`, que tiene prioridad sobre `.env.local` en `npm run dev`. `lib/supabase/client.ts` lanza un error al importarse si faltan, así que `npm run build` también las necesita. Los secretos de R2 nunca van en Next: viven en las Edge Functions (`supabase/functions/.env.example`).

Para probar en el navegador con datos del seed: códigos de alumno `TEST22`…`TEST29`, `TESTA2`…`TESTD2`; staff `admin@ejemplo.com`, `guia.uno@ejemplo.com` (San Pablo y San José) y `guia.dos@ejemplo.com` (Santa Rosa y Santa María), `catequista.uno@ejemplo.com` (solo pasa lista en San Pablo) y `mixto@ejemplo.com` (guía en Santa Rosa y catequista en San José) con cualquier contraseña de 6+ caracteres (el primer login crea la cuenta; requiere `NEXT_PUBLIC_LOGIN_CON_CORREO=true` en `.env.development.local`). Las fotos del seed no existen en R2 (se ven rotas); para fotos reales, súbelas por `/alumno`. Fuera del horario (sáb 19:00 → lun 23:59) se puede abrir el formulario a mano con `update public.ciclos set abierto_manual = true where activo` y volverlo a `null` al terminar.

## Flujo de ramas

- `main`: solo versiones listas para producción, por Pull Request desde `develop`.
- `develop`: integración; recibe cada fase o tarea por Pull Request.
- `feature/<nombre>`: se crea desde `develop` (`git switch -c feature/administracion develop`). Nunca commitear directo en `main` ni en `develop`.
- En GitHub los PR se unen con **"Create a merge commit"** (no squash ni rebase), para que los commits se conserven y el siguiente PR muestre solo lo nuevo. La CI (`.github/workflows/ci.yml`) corre en cada PR y en los push a `main` y `develop`.
- Cada versión se anota en `CHANGELOG.md` (Keep a Changelog, en español) y en `version` de `package.json` (y de `package-lock.json`); las notas del release de GitHub salen de ahí.

## Arquitectura

### Base de datos (`supabase/migrations/`)

- El alumno (rol `anon`) no tiene acceso a ninguna tabla: solo a las RPC `estado_formulario` e `identificar_alumno`. Los envíos de foto pasan por `preparar_envio`/`confirmar_envio`, que solo puede ejecutar `service_role` (Edge Functions). En el navegador, todo lo del alumno y lo público (su código, `subir-foto`, `/misas`) usa `supabasePublico` (`lib/supabase/client.ts`, sin sesión), para que funcione aunque en ese celular haya un guía o admin conectado: con el cliente normal iría con su sesión (`authenticated`) y `identificar_alumno` respondería 403. `identificar_alumno` y `preparar_envio` bloquean 15 minutos tras 30 códigos equivocados desde una IP o 3.000 en total (`_limite_intentos_superado`, tabla `intentos_codigo`): un salón en el WiFi del colegio comparte IP, así que no conviene bajar el límite por IP. La IP sale de los headers (`_ip_cliente`); en las fotos la pasa la Edge Function.
- El staff se identifica por el email del JWT (login con Google) contra `public.staff`; `es_admin()`, `es_staff_de()` y `es_staff_de_alumno()` alimentan las políticas RLS. La función de cada persona va **por comunidad** (`staff_comunidades.funcion`: `guia` o `catequista`), así que alguien puede ser guía en una comunidad y catequista en otra; `staff.rol` solo distingue al admin (global). `es_staff_de()` es "admin o **guía** de esa comunidad": todo lo de misa, fotos y códigos queda cerrado al catequista. Para pasar lista se usa `puede_pasar_lista()` (admin, guía o catequista). `mi_perfil_staff` devuelve `es_guia`/`es_catequista` para el menú. El hook `hook_antes_de_crear_usuario` impide crear cuentas a correos que no estén en `staff`. `asistencias` y `envios_foto` solo se modifican por RPC (`revisar_asistencia`, `justificar_falta`, `reasignar_asistencia`, `cerrar_semana`).
- Horario en hora de Lima: envío sáb 19:00 → lun 23:59, reenvío de rechazadas hasta mié 23:59, cierre automático (pg_cron, `_cerrar_semana_vencida`) el jueves 00:05, que no marca faltas si el formulario está forzado en «Cerrado» (`abierto_manual = false`: nadie pudo enviar foto; en vacaciones se deja «Automático» porque igual se pide ir a misa). La semana se calcula por el domingo de referencia (`domingo_de_referencia`): la misa del sábado cuenta para el domingo siguiente, y de jueves a sábado `estado_formulario().semana` ya es la semana que viene. El frontend no calcula horarios: solo formatea (`lib/utils/timeHelpers.ts`).
- `public.momento_actual()` permite simular la hora en tests con `set_config('app.ahora', ...)`.
- `asistencias.estado` ∈ `pendiente | validado | rechazado | inasistencia | justificada`, una fila por (`alumno_id`, `actividad`, `semana_numero`). Cada foto subida queda en `envios_foto` (las rechazadas no se borran) con su huella y fecha EXIF.
- Catequesis (`20261025000001_catequesis.sql`): va por **sesión con fecha** (la clase del sábado, eventos del domingo), no por semana, en `sesiones_catequesis` y `asistencias_catequesis` (`presente | tardanza | falta | justificada`; lo no marcado queda "sin marcar", sin faltas automáticas). Se lee con RLS (`puede_pasar_lista`) y se escribe solo por RPC: `crear_sesion_catequesis`, `crear_evento_catequesis` (solo admin, varias comunidades), `editar_sesion_catequesis`, `borrar_sesion_catequesis`, `marcar_catequesis` (`p_estado null` borra la marca), `marcar_todos_presentes`; y se consulta con `sesiones_de_comunidad`, `lista_de_sesion` (sin códigos) y `resumen_catequesis`. `identificar_alumno` devuelve también `catequesis`. El enum `actividad` tiene `'catequesis'` desde el esquema inicial, pero no se usa: `asistencias` es solo de misa.
- Misas cerca de mí (`20261027000001_misas.sql`): `iglesias` (uno de los 12 distritos de la provincia de Trujillo y una ubicación que debe caer en la provincia, lo que atrapa latitud y longitud invertidas) y `horarios_misa` (solo el sábado desde las 17:00 y el domingo; `dia` como `isodow`). No dependen del ciclo. Cualquiera las lee con `iglesias_con_misas()` (para `/misas`, sin código; la ubicación del alumno nunca llega a la base). Solo el admin escribe: `guardar_iglesia` e `importar_iglesias` (todo o nada) crean o actualizan la iglesia, reemplazan sus misas y la marcan revisada hoy; `activa` y el borrado van directo por RLS. El seed trae iglesias ficticias.
- Resumen del administrador (`20261103000001_resumen_admin.sql`): `resumen_admin(p_faltas_seguidas)` (definer, solo admin) devuelve en un jsonb lo del ciclo activo: `semanas` (con su domingo y si ya `cerrada`, es decir, venció su reenvío; hasta la semana más nueva con registros, nunca más allá del último domingo del ciclo), `comunidades` activas (alumnos activos, guías, fotos por revisar y la más antigua, catequesis y los conteos crudos de misa por semana y estado), `alejandose` (faltas o rechazos seguidos en semanas cerradas después de la última con foto; las justificadas no suman ni cortan) e `iglesias_sin_horario`. Solo cuenta: las reglas del porcentaje están en `lib/staff/resumen-admin.ts`. Desde `20261113000001_resumen_guia.sql` el cálculo vive en `_resumen(p_comunidades, p_faltas_seguidas)` (interna, sin permisos para nadie): `resumen_admin` le pasa todas las comunidades activas y suma `iglesias_sin_horario`; `resumen_guia` (definer, `authenticated`) le pasa solo las comunidades del ciclo activo donde `staff_actual_id()` es **guía** (donde solo es catequista no entra) e `iglesias_sin_horario` en 0.
- Avisos push (`20261109000001_avisos_push.sql`): `suscripciones_push` (una fila por celular, de un alumno o de un staff; RLS sin políticas y sin permisos para `anon` ni `authenticated`), que solo se toca por RPC. `registrar_aviso_alumno` valida el código con el mismo límite de intentos que `identificar_alumno`; `registrar_aviso_staff` usa `staff_actual_id()`; `quitar_aviso` borra por dirección; las dos de registro pasan por `_guardar_suscripcion`, que **solo acepta direcciones de los servicios de avisos** (Google, Apple, Mozilla, Microsoft: `enviar-avisos` llama a cada una, así que aceptar cualquier URL permitiría usar el servidor para llamar a otros sitios) y deja 5 celulares por persona. `avisos_para_enviar(p_tipo)` y `quitar_suscripciones` son solo de `service_role`. Tipos: `apertura` (todos los alumnos), `recordatorio` y `cierre` (los que no tienen registro esa semana), los tres solo con el formulario abierto; `revision` (cada guía con fotos pendientes donde es guía, y el admin con el total). Aviso de rechazo (`20261111000001_aviso_rechazo.sql`): tipo `rechazo`, solo para rechazos de la semana del formulario con el reenvío abierto y de hace más de 2 minutos (lo que dura "Deshacer" en la base); `_rechazos_por_avisar()` los busca y `avisos_para_enviar` (ahora `volatile`) los anota en `rechazos_avisados` (cada foto se avisa una vez; si rechazan la siguiente, se vuelve a avisar), pero solo los de alumnos con avisos activados. `_avisar_rechazos()` corre cada 15 minutos (`avisos-rechazo`) y solo llama a la función si hay a quién avisar. El texto no lleva el motivo del guía. pg_cron llama a `_pedir_avisos(tipo)`, que con pg_net llama a la función con la dirección y la clave de Vault (`avisos_url`, `avisos_clave`); sin ellas no hace nada.
- Al cambiar el esquema: nueva migración en `supabase/migrations/`, `npm run db:reset`, `npm run db:test` y `npm run db:types`. El repo es público: el seed solo lleva datos ficticios.

### Fotos

- Cloudflare R2 privado, nunca público ni borrado. Edge Functions (Deno, `supabase/functions/`, fuera de ESLint y tsconfig) con `@supabase/server`: `subir-foto` (auth `publishable`; acciones `preparar` → URL PUT firmada 5 min, y `confirmar` → HEAD en R2 + RPC) y `ver-fotos` (auth `user`; RLS decide qué URLs GET firmadas devuelve). `@supabase/server` no acepta las claves legacy (anon JWT): el frontend usa la clave publishable. El CORS lo maneja `_shared/cors.ts` con `ORIGENES_PERMITIDOS`; en local el gateway de Supabase responde `*` igual, así que la restricción solo se nota en producción.
- En el navegador (`lib/fotos/`): `procesarFoto` lee la fecha EXIF antes de comprimir, calcula la huella dHash (`huella.ts`, bigint con signo de 64 bits como la columna `huella`) y comprime a **JPEG** de 720 px (Safari no genera WebP desde canvas). `prepararFoto` deja la foto lista (`FotoLista`) y `enviarFotoLista` hace preparar → PUT → confirmar pensando en la mala señal: cada paso se reintenta solo (`ESPERAS_REINTENTO_MS`, 4 intentos) y lo hecho no se repite (`ProgresoEnvio`: si ya subió, solo confirma aunque pase el tiempo; `envio_ya_confirmado` cuenta como éxito porque la respuesta anterior se perdió; si venció la URL o el envío, prepara otro). Si no lo logra, `EnvioFoto` queda esperando la señal y reintenta al volver la conexión, al volver a la app y cada 30 s. La foto comprimida se guarda antes de subirla en IndexedDB (`lib/fotos/pendiente.ts`, una sola, como `ArrayBuffer`, con el código y la semana, en fila para que un borrado no se adelante a un guardado): al abrir la app se ofrece «Tienes una foto sin enviar» solo al mismo alumno y semana (`pendienteVigente`, 5 días). Se borra al enviarla, al elegir otra, con «No soy yo», con los errores de `ERRORES_QUE_DESCARTAN_LA_FOTO` y cuando `PanelAlumno` ya no ofrece enviar (`accion === null`); en iPhone importa, porque la foto tomada desde la app no queda en la galería. Si el navegador no deja guardar, todo funciona igual mientras la app siga abierta.

### Alumno (`/alumno`)

`app/alumno/page.tsx` orquesta: sin código recordado muestra `IngresoCodigo` (pide el código personal y confirma "¿Eres Ana P.?" antes de recordarlo); con código muestra `PanelAlumno` (semana actual con `EnvioFoto` si `accion` es `enviar`/`reenviar`, o el estado/cuenta regresiva; mientras la semana no tiene foto, un enlace "¿Dónde ir a misa?" a `/misas`; `LineaProgreso` junto al saludo con los domingos seguidos y el porcentaje de `progresoAlumno` y `textoProgreso` (`lib/alumno/progreso.ts`: las mismas reglas que `resumirAlumno` del guía; la semana en curso solo suma validada, y las justificadas y las pendientes no suman ni cortan la racha). Para que lo principal quepa en una pantalla, lo demás va plegado con `Plegable` (`components/ui/plegable.tsx`, sobre `<details>`): `HistorialSemanas` (6 semanas y "Ver todas"), `TuCatequesis` con las últimas sesiones de `catequesis`, que es opcional en el tipo por si la base no tiene la migración, y `Recordatorios` con los avisos push y "Agregar al calendario"; al final, `EnlacesPie`). "No soy yo" quita los avisos de ese celular. En `EnvioFoto`, `ConsejosFoto` deja siempre a la vista lo principal, **el rostro del alumno dentro del templo**, y el resto en "Ver más". "Agregar al calendario" abre `/recordatorio-misa.ics` (`app/recordatorio-misa.ics/route.ts`, estático con `dynamic = "force-static"`, armado por `armarIcs` de `lib/alumno/calendario.ts`): un evento que se repite cada sábado a las 19:00 de Lima, sin nada del alumno. El código se recuerda en `localStorage` mediante `useCodigoGuardado` (`useSyncExternalStore`; `undefined` mientras hidrata, así no hay parpadeo ni error de hidratación). Los textos de error salen de `lib/alumno/mensajes.ts`.

### Avisos push

Web Push con VAPID, gratis. Horarios (Lima): sábado 19:00 `apertura`, domingo 08:00 `recordatorio`, lunes 18:00 `cierre`, lunes 20:00 `revision` y, cada 15 minutos, `rechazo` (si hay rechazos nuevos). La Edge Function `enviar-avisos` (auth `secret:*`: cualquier clave secreta del proyecto en `apikey`; usa `npm:web-push`) pide `avisos_para_enviar`, cifra y manda cada aviso, y borra las suscripciones que responden 404 o 410. No registra las direcciones en los logs. Los textos no llevan datos del alumno. En el navegador, `lib/push/avisos.ts` (`useAvisos`, `activarAvisos`, `desactivarAvisos`, `consultarAvisos`, y las puras `soporteDeAvisos` y `claveABytes`) y `public/sw.js` (`push` y `notificationclick`). El permiso se pide desde un toque, nunca al abrir. En iPhone solo funcionan con la app instalada (iOS 16.4+): `soporteDeAvisos` devuelve `instalar`. **En `next dev` no hay service worker**, así que los botones no aparecen: para probarlos, `npm run build && npm start`. Un celular tiene una sola suscripción: si otra persona activa los avisos ahí, pasa a ser suya. Si cambian las claves VAPID, todos deben volver a activarlos.

### Ayuda (`/ayuda`)

Página pública (`app/ayuda/page.tsx` + `components/ayuda/pagina-ayuda.tsx`) con la guía rápida: "Para alumnos" (instalar, código, la foto con el rostro dentro del templo, horario, rechazos y "¿Qué hago si…?") y "Para guías" (entrar, revisar, criterio de validación, rechazar, deshacer, cambiar alumno, justificar, Resumen WhatsApp, códigos y Excel, catequesis, cierre del jueves). "Imprimir o guardar PDF" usa `window.print()`: cada parte sale en su hoja (`print:break-after-page`). Se llega por "Ayuda" en `EnlacesPie` y en el encabezado de `MarcoStaff` (a `/ayuda#guias`). Si cambia cómo se usa la app, hay que actualizarla.

### Misas cerca de mí (`/misas`)

Página pública, sin código (`app/misas/page.tsx` con su `metadata`, que muestra `PaginaMisas` de `components/misas/`). Pide `iglesias_con_misas()` una sola vez. "Usar mi ubicación" llama a `navigator.geolocation` solo al tocar el botón, y la ubicación vive en el estado de React (nunca en `localStorage` ni en la red) para ordenar con `distanciaKm` (`lib/misas/ubicacion.ts`); sin permiso se filtra por distrito. `TarjetaIglesia` marca con `marcarMisas` (`lib/misas/proxima.ts`, en hora de Lima) las misas que ya empezaron y la próxima, y "Cómo llegar" abre Google Maps (`enlaceComoLlegar`). Se llega por el botón "Misas cerca" de `IngresoCodigo` (arriba a la derecha, con `IconoIglesia` de `components/ui/icono-iglesia.tsx`), por el enlace dentro de la semana de `PanelAlumno` (solo mientras falta la foto) y por el atajo "Misas cerca" del manifest. Su botón de volver dice "Mi asistencia" si hay código guardado (`useCodigoGuardado`): `/alumno` abre directo el panel, sin pedirlo otra vez.

### Staff

Las páginas del staff usan `MarcoStaff` (`components/dashboard/marco-staff.tsx`): valida la sesión con `useSesionStaff` (`lib/staff/sesion.ts`; sin sesión manda a `/login`), muestra el encabezado y el menú (Revisión · Catequesis · Mi comunidad/Asistencia · Administración solo para admins; quien solo es catequista no tiene menú; fijo abajo en el celular y arriba desde `md`, por eso el `main` lleva relleno inferior con `env(safe-area-inset-bottom)`) y entrega el `perfil` a la página como render prop. `requiere` (`"guia"` por defecto, `"lista"` en Catequesis) decide quién entra según `es_guia`/`es_catequista`: al que solo es catequista lo manda a `/dashboard/catequesis` sin montar la página, así no pide fotos. `soloAdmin` bloquea la página a los guías. Los guías y admins tienen en el encabezado la campana `BotonAvisos` (`components/dashboard/boton-avisos.tsx`), y "Salir" quita los avisos de ese celular.

- **Login** (`/login`): en producción solo se entra con Google. El botón oficial (`BotonGoogle`, `components/login/boton-google.tsx`, con Google Identity Services) devuelve un ID token que se canjea con `signInWithIdToken` y un nonce (`lib/staff/google.ts`); así la ventana de Google muestra el nombre de la app y no el dominio de Supabase. Necesita `NEXT_PUBLIC_GOOGLE_CLIENT_ID` y el origen de la página en "Authorized JavaScript origins" del cliente OAuth. Si falta el Client ID o el script no carga en 8 s, queda la redirección de siempre (`signInWithOAuth`: vuelve a `/login`, que pasa a `/dashboard/inicio` si hay sesión o muestra el error del hook), que además se ofrece como "Entrar de otra forma". En local, Auth acepta tokens de Google si el `.env` de la raíz tiene `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID` (ver `supabase/config.toml`) y tu Gmail está en `staff`. Con `NEXT_PUBLIC_LOGIN_CON_CORREO=true` (solo local) aparece un formulario de correo que, si la cuenta no existe, la crea. Seguro extra: el hook rechaza proveedores distintos de Google salvo que `ajustes.permitir_login_correo` esté activo, y solo el seed lo activa (`db push` no corre el seed). Tras el login (y desde `/` con sesión) se pasa por `/dashboard/inicio` (`app/dashboard/inicio/page.tsx`), que solo decide la página: el admin a `/dashboard/admin` (Resumen), el guía a `/dashboard` (Revisión) y quien solo es catequista a `/dashboard/catequesis`. El menú "Revisión" sigue en `/dashboard` sin redirigir.
- **Revisión** (`/dashboard`, `PanelRevision`): `mi_perfil_staff` (rol y `semana_reciente`, la de la última misa), `cola_revision` (pendientes con el domingo de esa semana, la foto anterior del alumno y la parecida) y `resumen_semana` (estado de cada alumno, para `armarResumenWhatsApp`). Las RPC de lectura del staff son `security invoker`, así que RLS limita a sus comunidades. Las URLs de las fotos se piden a `ver-fotos` con caché de 4 min (`lib/staff/fotos.ts`). Las fotos se muestran con `<img>` y no con `next/image` a propósito: así no pasan por el optimizador de Vercel.
- `TarjetaRevision`: swipe derecha valida, izquierda abre `ModalRechazo` (el motivo lo ve el alumno). Tocar la foto (sin arrastrar) o la lupa abre `VisorFoto` (pantalla completa sobre `<dialog>`, zoom). En PC (`lg`) los botones y lo que llega por la prop `lateral` (fotos para comparar, cambiar alumno) van a la derecha de la tarjeta, y hay atajos de teclado (`lib/staff/atajos.ts`: → o V valida, ← o R rechaza, Z deshace; no actúan escribiendo ni con un modal abierto). El consejo de la primera vez se recuerda con `useConsejoVisto` (`lib/staff/consejo.ts`, sobre `crearMarcaVista`). "Deshacer" se ofrece 8 s en la UI; la base lo permite 2 min al mismo revisor. "Cambiar alumno" (`ModalReasignar`) pasa una foto pendiente a otro alumno de la comunidad. Los avisos (`lib/staff/avisos.ts`) marcan fotos parecidas y fotos tomadas antes del sábado de esa semana.
- **Mi comunidad** (`/dashboard/comunidad`, `components/comunidad/`): para el guía, `PestanasComunidad` muestra «Resumen» (la que abre: `SeccionResumen` con `alcance="guia"`, que pide `resumen_guia`, oculta lo que configura el admin y la tabla por comunidad si tiene una sola; «Ver asistencia» cambia de pestaña con `onVerComunidad`) y «Asistencia»; el admin va directo a la matriz, y `?comunidad=ID` abre Asistencia. Asistencia es la matriz alumno × semana (la más reciente primero) con el porcentaje de `resumirAlumno` (`lib/staff/estadisticas.ts`: no cuenta justificadas ni pendientes); tocar una celda abre "justificar falta"; "nuevo código" usa la RPC `regenerar_codigo`; "Imprimir códigos" usa `window.print()` con las tarjetas de `CodigosImprimibles` (solo visibles con `print:`) y "Descargar Excel" el `.xlsx` de la comunidad (`tablaAsistencia`). `?comunidad=ID` abre esa comunidad (lo usa el Resumen); por `useSearchParams`, `VistaComunidad` va dentro de `<Suspense>`.
- **Catequesis** (`/dashboard/catequesis`, `components/catequesis/`, `lib/staff/catequesis.ts`): comunidades con `obtenerComunidadesVisibles` (donde pasa lista; `obtenerMisComunidades` da solo las de guía, para Mi comunidad). Pestaña "Pasar lista": sesiones con sus conteos, "Nueva sesión" (fecha de hoy con `hoyEnLima`) y, para el admin, "Nuevo evento para varias comunidades". `PasarLista` guarda cada toque al instante en una cola por alumno (la última marca gana), con "Reintentar" si falla; tocar la marca elegida la borra y la J pide el motivo (`ModalMotivo`). Pestaña "Resumen": matriz alumno × sesión con `resumirCatequesis` (la tardanza cuenta como asistencia) y el Excel de `tablaCatequesis`. Cómo se ve cada marca: `ESTADOS_CATEQUESIS` en `lib/ui/estados.ts`.
- **Administración** (`/dashboard/admin`, `components/admin/`): pestañas Resumen (la que abre: `SeccionResumen` con `obtenerResumen` + `armarResumen` de `lib/staff/resumen-admin.ts`; tarjetas de la última semana cerrada, la semana en curso, fotos por revisar y catequesis; tabla por comunidad con enlace a su asistencia; "Necesitan atención" con los alumnos de `FALTAS_PARA_ALERTA` faltas seguidas, comunidades sin guía e iglesias sin horario; y la tendencia en barras CSS. Los porcentajes siguen las reglas de `resumirAlumno` y `resumirCatequesis`, como el Excel), Reportes y, tras una raya, lo de inicio de año: Ciclo (fechas, formulario automático/abierto/cerrado, crear ciclo, `copiar_comunidades` y `activar_ciclo`), Comunidades, Staff (Gmail, rol, y por comunidad "Guía en" / "Catequista en" con `asignarComunidad`; pasar de catequista a guía pide confirmación), Alumnos (pegar desde Excel con `parsearNombres` y la RPC `importar_alumnos`, que descarta repetidos) Reportes (Excel de misa del ciclo con `tablaAsistencia`, Excel de catequesis del ciclo en formato largo con `datosCatequesisCiclo` + `tablaCatequesisCiclo`, y cierre manual de semana) y Misas (`SeccionMisas` + `ModalIglesia`, con la lógica en `lib/misas/`: "Descargar plantilla (Excel)" da `plantillaIglesias()` —hoja "Iglesias" con Nombre | Distrito (lista desplegable) | Dirección | Ubicación | Teléfono | Sábado | Domingo | Notas, una fila de ejemplo que nunca se importa, y la hoja "Cómo llenar"—; "Subir Excel" la lee con `leerExcel` y `parsearCeldasIglesias`, y también se pueden pegar filas, que van por `parsearFilasIglesias`. Con encabezado, las columnas se reconocen por su nombre y en cualquier orden, y se acepta la columna Misas de antes; sin encabezado van en el orden de la plantilla. Las horas se leen con `parsearMisas` anteponiendo el día ("Sáb 19:00; Dom 7:00, 9:00 y 11:00") y la ubicación con `parsearUbicacion`, tal como la copia Google Maps. Todo se valida antes de `importar_iglesias`, y "Descargar la lista" arma el mismo Excel con `libroIglesias` para editarlo y volver a subirlo). Las escrituras simples van directo a las tablas (RLS solo deja al admin); los errores se traducen con `mensajeDe` (`lib/staff/errores.ts`). Las listas largas usan `obtenerTodasLasFilas` (`lib/supabase/paginacion.ts`, Supabase corta en 1000 filas). Las acciones que no se deshacen solas (activar ciclo, dar de baja, desactivar, código nuevo, cerrar semana, hacer administrador) piden confirmación con `useConfirmar`; la matriz, Alumnos y Staff se filtran con `Buscador` + `coincide` (`lib/staff/busqueda.ts`, sin importar mayúsculas ni tildes).
- **Excel** (`lib/excel/`): todos los "Descargar Excel" dan un `.xlsx` de verdad (no CSV, que el Excel en español abre en una sola columna). Los datos se arman como `Tabla` (`tabla.ts`, lógica pura con tests: columnas con ancho, `formato` texto o porcentaje, lista desplegable y nota) y `libro.ts` los convierte con ExcelJS (`crearLibro`, `descargarExcel`, `leerExcel`). ExcelJS pesa unos 250 KB: se importa con `import()` solo al descargar o subir, así que no llega al alumno ni a `/misas` (de `lib/misas/importacion.ts` solo se importa el tipo `Tabla`). Un texto que empieza con `=` queda como texto, nunca como fórmula. `textoDeCelda` devuelve como "19:00" las horas que Excel convirtió solas.

### Convenciones de React

En los `useEffect` no llames funciones que hagan `setState` de forma síncrona (la regla `react-hooks/set-state-in-effect` lo marca como error): separa la consulta (devuelve datos) de la aplicación al estado y haz `consultar().then(aplicar)` dentro del efecto, como en `app/alumno/page.tsx`. En timers, el `setState` va dentro del callback (ver `formulario-cerrado.tsx`).

### PWA

`public/manifest.json` y un `public/sw.js` escrito a mano que solo guarda los archivos de la app (`/_next/static/`, íconos, manifest): nunca fotos, datos ni llamadas a Supabase o R2. También muestra los avisos push. Lo registra `components/service-worker-registrar.tsx` solo en producción (en `next dev` lo desregistra). `next.config.ts` añade los headers de `/sw.js`. Si cambias lo que se cachea (o el manifest, que se sirve desde la caché), sube `CACHE_NAME`: la activación borra las cachés viejas.

La app instalada abre en `/` (`app/page.tsx`), que decide en el navegador porque la sesión del staff vive en localStorage: con sesión va a `/dashboard/inicio` y sin ella a `/alumno`. Como la app instalada no tiene barra de direcciones, el staff llega a `/login` por el enlace "¿Eres guía, catequista o administrador?" de `IngresoCodigo` o, en Android, por el atajo "Panel del staff" del manifest (`shortcuts`). Por lo mismo, `/login` tiene "¿Eres alumno? Volver a poner tu código" para el alumno que entró por error.

Ayuda para instalar: `/instalar` (`components/pwa/pagina-instalar.tsx`) muestra los pasos de Android y de iPhone (primero los del celular que se usa, según `plataformaDe` de `lib/pwa/instalacion.ts`) y, en Chrome/Edge, un botón que abre la ventana del sistema. Ese aviso (`beforeinstallprompt`) llega una sola vez por carga, casi siempre en la primera página: lo captura `escucharInstalacion`, llamado desde `ServiceWorkerRegistrar`, y no se cancela para que Chrome siga mostrando su aviso "Instalar". `useAppInstalada` (modo standalone) oculta "Cómo instalar" en el pie `EnlacesPie` ("Ayuda · Cómo instalar · Privacidad", en la pantalla del código, el panel del alumno, `/login` y `/misas`). Las tarjetas impresas de códigos (`CodigosImprimibles`) también dicen cómo instalarla.

Íconos y logo: la app instalada se llama "Mi Misa PS" (`short_name`; `name` "Mi Misa PS · Pastoral Mariana") y sus íconos llevan el óvalo sobre el azul de la marca con una insignia ✓, para no confundirla con Pastoral Digital (la app de catequistas, que usa el mismo óvalo sobre blanco); el logo dentro de la interfaz no cambia. `node scripts/generar-iconos.mjs` genera `app/icon.png`, `app/apple-icon.png`, `public/icons/*` y `marca/web/*.webp` desde `marca/` (usa `marca/logo-completo.png` y `marca/logo-ovalo.png` si existen; si no, recorta el óvalo de `marca/logo-original.jpg`). También genera `marca/web/logo-completo-oscuro.webp` para el tema oscuro, pintando de blanco solo las letras de `logo-completo.png` (el óvalo queda igual; si cambias ese archivo, vuelve a medir `OVALO_EN_COMPLETO`). Al cambiar el logo, vuelve a correrlo y sube `CACHE_NAME`. En la UI el logo va con `LogoCompleto` (cambia de versión según el tema) y `LogoOvalo` (`components/ui/logo.tsx`).

### Estilos

Tailwind v4 sin `tailwind.config`. Tema automático claro/oscuro con los colores del logo de la Pastoral Mariana: las variables de `app/globals.css` cambian con `prefers-color-scheme` y se usan como clases con nombre (`bg-fondo`, `bg-superficie`, `bg-superficie-2`, `border-borde`, `text-texto`, `text-texto-suave`, `text-texto-tenue`, `text-marca`, `bg-marca-solido`, `text-exito`/`error`/`aviso`/`info`, `bg-*-solido` para botones y tintes como `bg-error/10`). **No uses colores fijos** (`white/*`, `rose-*`, `neutral-*`…): solo quedan `text-white` sobre botones sólidos y sobre las fotos, y los `neutral` de impresión. `lib/ui/contraste.test.ts` comprueba que cada texto tenga contraste ≥ 4.5:1 en los dos temas. Clases propias: `tarjeta` (`@utility`), `animate-fade-in`, `animate-fade-in-scale`, `delay-100`…`delay-400` (como `animation-delay`); las animaciones se apagan con `prefers-reduced-motion`. Está pensada para móvil. Como `viewportFit` es `cover`, en iPhone con la app instalada la página ocupa también la franja de la hora: `body` reserva `env(safe-area-inset-top)` y `body::before` la tapa con el fondo, para que nada pase por debajo al hacer scroll.

Piezas compartidas en `components/ui/`: `base.tsx` (`Boton` con `variante`/`tamano` y mínimo 44 px, `claseInput`, `claseDeBoton`, que vive en `clases.ts` sin "use client" para poder usarse en páginas de servidor, `Campo`, `Tarjeta`, `Mensaje`, `Cargando`), `modal.tsx` (`Modal` sobre `<dialog>`: Escape, foco atrapado, `data-autofocus`) y `confirmar.tsx` (`useConfirmar`, en lugar de `window.confirm`). Cómo se muestra cada estado de una semana: `lib/ui/estados.ts`.

Alias de imports: `@/*` apunta a la raíz del repo.
